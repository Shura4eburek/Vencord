## Дорожная карта: полноценный P2P без зависимости от Discord

Цель: звонки (в том числе групповые) и чат работают по P2P, даже когда у Discord проблемы. Бесплатно,
без своих серверов (сигналинг и офлайн-доставка — через релеи Nostr). Каждый шаг — отдельная фича
spec-kit, по порядку: следующий опирается на предыдущий.

1. [~] **Ключи и контакты** (`specs/003-identity-keys`) — сделано, ждёт живой проверки. Своя пара ключей у каждой установки; обмен ключами с
   собеседником, пока Discord работает; локальная книга контактов (имя, аватар, ключ). Закрывает дыру
   «ключ пары подбирается перебором» (раздел «Безопасность»). Без этого шага офлайн невозможен: сейчас
   собеседник определяется по Discord ID, а ключ — по ID ЛС-канала.
2. [ ] **Групповые звонки** — план ниже, в «Безопасность и инфраструктура» (входящий во время звонка,
   «Добавить сюда», состав звонка у всех, mesh).
3. [ ] **P2P-чат.** Сообщения напрямую по WebRTC, пока собеседник в сети; иначе зашифрованно через релеи
   (получит при входе); история локально; затем групповые чаты.
4. [ ] **Офлайн-окно P2PCall.** Своё окно из main-процесса (он стартует и без серверов Discord): контакты,
   чат, звонки — без веб-клиента Discord.

## Баги

- [x] **«Собеседник занят» после перезапуска Discord.** Исправлено: `ring` от того же собеседника с новым `callId` завершает старый звонок и принимает новый (кроме встречного дозвона). Если один из собеседников перезапустил Discord посреди
  звонка, при новом вызове второй отвечает «занят» — ему приходится вручную сбросить «висящий» звонок.
  Вероятная причина: закрытие Discord не отправляет `bye`, у второго звонок остаётся активным со старым
  `callId`, и `reduce` отвечает на новый `ring` `decline busy`.
  Варианты: `bye` при `beforeunload`; `ring` от того же собеседника во время активного звонка с ним =
  «переподключился» → завершить старый, принять новый.
- [ ] **Битрейт отправки держится ~4–5 Мбит/с с `limit=bandwidth`**, хотя приём от собеседника шёл 12–15 Мбит/с.
  Нужно в лог `availableOutgoingBitrate` из `candidate-pair` и разобрать, режет ли оценка канала (GCC) или
  стартовый битрейт не применился.
- [ ] **AV1 никогда не выбирается.** `probeCaps` возвращает `encodeHw: []`, хотя статистика показывает
  аппаратный H.264 (`powerEfficientEncoder: true`). Проба `mediaCapabilities` для `webrtc` не отражает
  реальность — выбирать по факту (`RTCRtpSender.getCapabilities` + `powerEfficientEncoder` из статистики)
  или пробовать AV1 и откатываться.
- [ ] **Окно входящего звонка, закрытое через Esc**, может не отклонить звонок (Discord закрывает модалку
  мимо нашего `onClose`) — звонок звенит до таймаута 30 с.

## Демка

- [x] 30 FPS вместо выбранного — исправлено: `getDisplayMedia` через свой обработчик, стабильные 60 на 1440p.
- [ ] **Больше 60 FPS — нативный стек (разведка пройдена 2026-10-06).** Chromium/WGC не отдаёт > 60 (проверено
  в Discord и Chrome). Рабочая схема, проверенная в петле на одной машине (Chrome 154, RTX 4070 Ti, 1440p):
  - захват DXGI (`ffmpeg ddagrab`, `framerate` с запасом выше частоты монитора, затем `fps=144`) + `h264_nvenc`
    → 144 FPS, GPU ~38 %;
  - в WebRTC идёт пустой трек 16×16; Encoded Transform приклеивает к каждому его кадру все накопившиеся кадры
    NVENC (маркер SEI + длина); получатель их отрезает и декодирует WebCodecs (`avc1.640034`, аппаратно),
    пустышку возвращает в WebRTC — иначе тот шлёт PLI;
  - результат: 144,1 FPS декодирования 2560×1440, задержка ffmpeg→декод p50 10 мс / p95 20 мс;
  - декодер WebRTC для 1440p не годится (20–37 FPS), поэтому только WebCodecs;
  - обязательно: битрейт кодера на лету под `availableOutgoingBitrate` (иначе очередь и задержка в секундах),
    свой запрос ключевого кадра по data channel, пересоздание WebCodecs при ошибке;
  - у PC с `encodedInsertableStreams: true` приёмник обязан пропускать кадры через `createEncodedStreams`.
  Открытый выбор: ffmpeg (быстрее, но без смены битрейта на лету) или свой нативный модуль (WGC/DXGI + NVENC/MF).
- [ ] Окно выбора первые 0,5 с показывает 60 до замера частоты монитора.
- [ ] Чип: у строки «↑» общий исходящий битрейт (звук + камера + демка), а не только демки.

## Безопасность и инфраструктура

- [~] **Ключ пары для сигналинга.** Было: ключ из ID канала, подбирался перебором по публичной подсказке.
  Стало (`specs/003-identity-keys`): обмен ключами по CPace на ID ЛС, ключ пары на устройство, подсказка от
  него; старая схема отключена совсем. Ждёт живой проверки.
- [x] Собеседник у того же провайдера (двойной NAT, несимметричный маршрут) — UDP-туннель с UPnP
  (`specs/001-udp-tunnel-upnp`), проверено вживую 2026-10-18: путь «туннель», rtt 2–4 мс.
- [ ] **Групповые звонки (mesh на 3–5 человек).** План:
  - [ ] **Баг: входящий P2P-звонок во время звонка не виден.** Сейчас `reduce` молча отвечает новому
    звонящему `decline busy` — у нас ни окна, ни уведомления, у него сразу «занят». Нужно окно входящего
    звонка и во время звонка: «Отклонить», «Положить текущий и принять», «Добавить сюда».
  - [ ] **«Добавить сюда»** — принять входящий звонок в текущий: звонок становится групповым (сразу,
    без отдельного «создать группу»). Та же кнопка нужна и для исходящего: звоню третьему, будучи в
    звонке, — он добавляется к текущему, а не «занят».
  - [ ] **Первый шаг — состав звонка у всех.** Когда в звонок добавляется человек, его тег (ID и имя
    пользователя) рассылается всем участникам: «X теперь с нами в звонке». У каждого участника звонок
    виден в ЛС с каждым другим участником — например, втроём Mamoru, Reva1v и doomer: у Mamoru в ЛС и с
    Reva1v, и с doomer; у Reva1v — в ЛС с Mamoru и с doomer; у doomer — в ЛС с Mamoru и с Reva1v.
  - [ ] Медиа: mesh — отдельное соединение (и туннель, если нужен) с каждым участником; ограничение по
    аплинку для демки на 3+ человек.
