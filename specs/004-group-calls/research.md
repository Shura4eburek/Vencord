# Research: групповые звонки P2PCall

Исходная точка (код на 2026-10-18): `state.ts` — автомат одного звонка вдвоём (`Peer` = callId + peerId +
channelId); `controller.ts` держит одну `Session`, один туннель, один `<audio>` и один `LevelMeter`
собеседника; `signaling.ts` — комната на callId с одним `PeerCtx`; `net.ts` — один активный туннель
(`active`) и один файл зависшего проброса; входящий во время звонка — `decline busy` в `reduce`.

## R1. Звонок = группа + связи с каждым участником

- **Decision**: разделить «звонок» и «связь». **Группа** (`groupId`, состав) — новый чистый модуль
  `group.ts` с редьюсером и тестами. **Связь** (`linkId`) — пара «я ↔ участник»: свой `Session`, туннель,
  комната сигналинга, `<audio>`, `LevelMeter`, таймер ICE. Контроллер держит `Map<userId, PeerLink>`.
  Существующий `reduce` остаётся автоматом **вызова** (ring/accept/decline/таймаут) — для первого
  звонка и для каждого приглашения; после принятия связь передаётся в группу.
- **Rationale**: автомат вызова уже отлажен и покрыт тестами; групповые правила (состав, сходимость, уход)
  — отдельная задача, которую проще проверить чистыми функциями. Звонок вдвоём = группа из двух —
  один путь кода, а не два.
- **Alternatives**: расширить `CallState` массивом собеседников — автомат вызова и состав перемешаются,
  а переходы `ended` / `busy` становятся неоднозначными; SFU — нужен сервер, против цели «без серверов».

## R2. Идентификаторы: `groupId` и `linkId`

- **Decision**: `groupId` = `callId` первой связи звонка (у звонка вдвоём он такой же, как сейчас).
  У каждой связи свой случайный `linkId` — он идёт в поле `callId` сигнала, топик комнаты — как сейчас
  `topicCall(linkId)`. Групповые поля (`group`) добавляются в сообщения рядом.
- **Rationale**: `Signaling` (комната = один собеседник) и `net.ts` (туннель по callId) работают по связи
  без изменений протокола; старая версия видит обычный звонок вдвоём.
- **Alternatives**: одна комната на группу — понадобился бы общий групповой ключ и его смена при уходе.

## R3. Совместимость со старыми версиями

- **Decision**: `ring` и `accept` новой версии несут `caps: ["group"]`. Звонок вдвоём со старой версией —
  как сейчас. Добавить в группу участника без `caps` нельзя: если звонок уже групповой, исходящий вызов не
  отправляется («у X старая версия P2PCall»); если в его `accept` нет `caps`, а звонок стал групповым —
  связь с ним закрывается `bye`, остальные видят «у X старая версия». Последние известные `caps` контакта
  запоминаются в памяти (по любому его сообщению), чтобы предупредить до вызова.
- **Rationale**: старый клиент игнорирует незнакомые поля и типы (`onSignal` — `switch` без `default`),
  поэтому новые сообщения ему безвредны.

## R4. Ключи участников, которые не контакты друг друга

- **Decision**: **представление**. Добавивший (A) отправляет новому (C) по ключу пары A–C список текущих
  участников: `{ userId, name, avatar, deviceId, publicKey }`; каждому текущему участнику B — то же о C.
  Получатель передаёт это в main (`contactIntroduce`), main кладёт устройство в книгу контактов с
  `via: A`. Ключ пары B–C — тот же `pairKey(own, peerPub, peerDeviceId)`, что и в `003`: он симметричен,
  обмен по CPace не нужен. Правила `003`: первый ключ контакта — `trusted`, другой ключ известного контакта
  — `pending` (связь с ним не устанавливается до подтверждения). Свой ключ из представления не
  перезаписывает ключ, полученный CPace.
- **Rationale**: у B и C может не быть общего ЛС → CPace невозможен (пароль — ID ЛС). Доверие добавившему
  принято в спецификации (Assumptions). На релеи уходит только шифротекст по ключу пары A–B / A–C.
- **Alternatives**: групповой ключ на звонок — тот же уровень доверия к A, но нужно его менять при уходе
  и он не даёт контакта на будущее; CPace через Discord ID — пароль публичен.
- **Безопасность**: A может подменить ключ B для C (MITM). Это то же доверие, что в групповом звонке Discord;
  записывается в контакт как `via`, в списке контактов видно «получен через A».

## R5. Кто кому устанавливает связь (без встречных вызовов)

- **Decision**: связь между двумя участниками группы, которой ещё нет, начинает тот, чей Discord ID
  **меньше** (как `isPolite`), сообщением `link` (это `ring` с `group.id` и `auto: true`). Получатель
  принимает его без окна, если `group.id` — его текущая группа и отправитель есть в составе; иначе
  игнорирует. Пока у получателя нет ключа (представление ещё не дошло), событие с релея он не расшифрует —
  поэтому `link` повторяется каждые 2 с до `accept`, не дольше 15 с.
- **Rationale**: детерминированное правило убирает встречный дозвон между участниками; события kind 25050
  эфемерные (релей их не хранит), повтор — единственный способ пережить гонку «ключ ещё не пришёл».
- **Alternatives**: соединения инициирует только новый участник — гонка, если двое добавлены одновременно.

## R6. Состав и его сходимость

- **Decision**: состав — множество записей `{ userId, joinedAt, by }` плюс «надгробия»
  `{ userId, leftAt }`. Слияние: участник есть, если его последний `joinedAt` больше последнего `leftAt`.
  Любое изменение рассылается всем участникам по их связям (`roster` — полный состав, а не дельта); при
  установке новой связи стороны обмениваются полным составом. Чистая функция `mergeRoster` + тесты на
  одновременные добавления и уходы.
- **Rationale**: несколько участников меняют состав одновременно; полное состояние с идемпотентным
  слиянием (CRDT «последняя запись побеждает» по времени) сходится без координатора — «главного» нет.
  Часы участников могут расходиться — `joinedAt` ставит тот, кто добавил, повторное вступление после
  перезапуска даёт новый `joinedAt` (он заведомо позже).
- **Alternatives**: состав ведёт добавивший — при его уходе звонок теряет «хозяина».

## R7. Уход и пропажа участника

- **Decision**: явный уход — `leave` всем (по связям) → надгробие. Пропажа без `leave`: каждая связь шлёт
  `here` каждые 5 с по сигналингу; нет `here` от участника 15 с — локально надгробие и уведомление «X
  вышел» (каждый приходит к этому сам, рассылать чужой уход не нужно). Нет медиасвязи с участником, но
  `here` идёт — он остаётся в составе с пометкой «нет связи». Остался один — звонок завершён.
- **Rationale**: ICE `disconnected` между двумя участниками не означает ухода из звонка (Edge Case
  «не может соединиться с одним»); сигналинг — общий для всех канал. 5 человек: 20 сообщений / 5 с —
  для релеев незаметно.
- **Alternatives**: решение по ICE — ложные уходы при частичной связности.

## R8. Входящий во время звонка и приглашения

- **Decision**: в контроллере очередь **приглашений** (входящих вызовов, пока идёт звонок): каждое — свой
  экземпляр автомата `reduce` (`incoming`), свой таймер, своё окно. Действия: «Отклонить» (`decline`),
  «Положить текущий и принять» (`leave` группы → `accept`), «Добавить сюда» (`accept` + представление
  составам). Ветка `decline busy` в `reduce` остаётся только для `auto`-связей чужих групп и для
  переполненной группы (5). Окно закрывается Esc/крестиком — `decline` (обработчик `onClose` уже есть;
  баг из todo про Esc — проверить, что `Modal` вызывает `onClose` и для Esc, иначе слушать `keydown`).
- **Исходящий во время звонка**: кнопка звонка в ЛС с X при идущем звонке = `invite(X)`: обычный `ring`
  с `group` (состав) — у X окно входящего с пометкой «групповой звонок: A, B».
- **Rationale**: несколько входящих одновременно (Edge Case) — независимые автоматы.

## R9. Медиа в mesh

- **Decision**: локальные треки (микрофон, камера, демка) захватываются один раз и добавляются во все
  `Session`. Свой `<audio>` и `LevelMeter` на каждого участника; «оглушение» глушит все. Приоритет
  `RTCRtpSender`: звук `priority: "high"`, видео `"low"` — при перегрузке аплинка браузер режет видео.
  Демка: потолок битрейта выбранного качества делится на число получателей
  (`maxBitrate = quality / (n − 1)`, не ниже 1,5 Мбит/с), дальше GCC каждой связи снижает сам.
  Поверх — существующая логика качества (`streamQuality.ts`) на общем захвате.
- **Rationale**: один захват — одна нагрузка на кодирование с захвата; кодирование всё равно на
  каждого получателя (по свойству WebRTC без SFU) — для 4 получателей демки 1080p60 на аппаратном H.264
  это допустимо. Simulcast бесполезен без SFU.
- **Alternatives**: один участник «ретранслирует» демку — нагрузка и задержка на нём, сложнее.

## R10. Туннели на несколько связей

- **Decision**: `net.ts` — `Map<linkId, ActiveTunnel>` вместо одного `active`; файл зависших пробросов —
  список. Порт у каждой связи свой (как сейчас — случайный из 40000–41000). `netLoader` перезагружает
  модуль только без активных туннелей — как сейчас, условие «ни одного».
- **Rationale**: каждая связь может нуждаться в туннеле (тот же провайдер у любой пары); туннель уже
  привязан к callId — меняется только учёт.

## R11. Где виден звонок

- **Decision**: `areaVisible(state, channelId)` — звонок виден в ЛС с любым участником группы, если такой
  ЛС есть у этого клиента (`dmPeers()`), иначе в ЛС с добавившим. Окно звонка — сетка плиток на всех
  участников (имя, аватар, индикатор речи, «нет связи», видео); раскладка: 2 — как сейчас, 3–5 — сетка.
- **Rationale**: FR-009/FR-010; канал определяется на клиенте — ID чужих ЛС не передаются.

## R12. Что не меняется

- Обмен ключами `003`, формат шифрования сигналинга, релеи, автообновление.
- Звонок вдвоём для пользователя выглядит как раньше (SC-007).
