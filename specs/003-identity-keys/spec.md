# Feature Specification: Ключи и контакты P2PCall

**Feature Branch**: `feat/p2p-call`

**Created**: 2026-10-18

**Status**: Draft

**Input**: User description: "Шаг 1 дорожной карты полноценного P2P без зависимости от Discord: своя пара ключей у каждой установки, обмен ключами с собеседником, пока Discord работает, локальная книга контактов (имя, аватар, ключ). Закрыть дыру «ключ пары подбирается перебором»."

## Контекст

Сейчас ключ шифрования сигналинга выводится из ID ЛС-канала, а в каждом звонке на публичные релеи уходит
подсказка, по которой этот ключ подбирается перебором. Посторонний на релеях может прочитать адреса
собеседников и вклиниться в звонок. Кроме того, собеседник определяется только через Discord (ID и список
ЛС), поэтому без Discord звонить некому. Этот шаг даёт каждому собеседнику собственные ключи и локальную
книгу контактов — основу для групповых звонков, P2P-чата и офлайн-окна.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Контакт появляется сам (Priority: P1)

Mamoru и друг оба с P2PCall и общим ЛС. Без каких-либо действий с их стороны они обмениваются ключами,
и у каждого появляется контакт другого: имя, аватар, ключ. Звонки между ними дальше шифруются этими
ключами, а не ключом из ID канала.

**Why this priority**: основа всего — без ключей нет ни защиты, ни офлайна.

**Independent Test**: двое с новой версией открывают общий ЛС → в настройках плагина у каждого виден
контакт другого; звонок проходит; на релеях нет данных, по которым можно получить ключ.

**Acceptance Scenarios**:

1. **Given** у обоих новая версия и общий ЛС, **When** любой из них открывает этот ЛС или звонит, **Then**
   в течение 10 с у обоих появляется контакт другого с его ключом.
2. **Given** контакт есть, **When** идёт звонок, **Then** сигналинг шифруется ключами пары, а не ключом
   из ID канала, и на релеи не уходит ничего, из чего этот ключ выводится.
3. **Given** контакт есть, **When** Discord перезапущен, **Then** контакт и ключи на месте (хранятся локально).

---

### User Story 2 - Подмена ключа не проходит незаметно (Priority: P1)

Кто-то пытается выдать себя за собеседника своим ключом. Плагин не принимает такой ключ молча.

**Why this priority**: иначе собственные ключи ничего не защищают.

**Independent Test**: подсунуть контакту другой ключ от имени того же пользователя → звонок с подменённым
ключом не устанавливается, пользователь видит предупреждение.

**Acceptance Scenarios**:

1. **Given** у контакта уже сохранён ключ, **When** приходит другой ключ от его имени, **Then** звонки с
   новым ключом не принимаются, пока пользователь явно не подтвердит смену, и показывается предупреждение.
2. **Given** пользователь хочет удостовериться, что ключ настоящий, **When** он открывает контакт, **Then**
   видит код проверки, который можно сверить с собеседником голосом. Совпали коды — ключи
   настоящие, даже если первый обмен подменил сам Discord; контакт помечается «проверен».

---

### User Story 3 - Старые версии и переход (Priority: P2)

Собеседник ещё на старой версии без ключей. Звонки с ним продолжают работать, как раньше; после его
обновления пара переходит на ключи сама.

**Why this priority**: переход не должен ломать звонки, но это временная ситуация.

**Independent Test**: звонок новой версии со старой проходит; после обновления старой — следующий звонок
идёт на ключах пары.

**Acceptance Scenarios**:

1. **Given** у собеседника версия без ключей, **When** идёт звонок, **Then** он работает по прежней схеме — пока
   у этого собеседника нет ключей. После первого обмена ключами старая схема с ним отключается навсегда.
2. **Given** собеседник обновился, **When** следующий звонок, **Then** пара использует ключи без действий
   пользователей.

---

### Edge Cases

- Один аккаунт Discord на двух ПК: у каждой установки свой ключ; у контакта хранится несколько ключей
  одного пользователя, звонок доходит до всех его устройств, как сейчас.
- Плагин переустановлен (ключи потеряны): новый ключ от того же пользователя — это сценарий US2/AC1
  (предупреждение и подтверждение).
- Собеседник удалил ЛС или заблокирован в Discord: контакт остаётся в книге, пользователь может удалить
  его вручную.
- Обмен ключами начался, но один из собеседников вышел посередине: при следующей встрече обмен завершается.
- Ключи хранятся на диске пользователя: другой пользователь Windows того же ПК не должен иметь к ним доступа
  без прав этого пользователя.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Каждая установка MUST иметь собственную пару ключей, созданную при первом запуске и
  хранящуюся локально.
- **FR-002**: Ключи собеседников MUST обмениваться автоматически, пока у обоих работает Discord, через
  релеи по протоколу обмена ключами по паролю (PAKE), где общим секретом служит ID их ЛС-канала: без
  сообщений в Discord, без своего сервера и без входа. Ни одно отправленное на релеи сообщение не позволяет
  проверить догадку об ID канала без живого обмена с плагином собеседника; живые попытки ограничены по
  частоте.
- **FR-003**: Книга контактов MUST хранить для каждого собеседника: Discord ID, имя, аватар, ключи
  устройств, время добавления; MUST переживать перезапуск Discord.
- **FR-004**: Сигналинг звонка с контактом MUST шифроваться ключами пары; на релеи MUST NOT уходить данные,
  из которых этот ключ можно вывести или подобрать.
- **FR-005**: Смена ключа известного контакта MUST NOT приниматься молча: предупреждение и явное
  подтверждение пользователя.
- **FR-006**: Пользователь MUST видеть список контактов в настройках плагина и мочь удалить контакт.
- **FR-007**: Прежняя схема (ключ из ID канала) MUST NOT использоваться совсем (решение после ревью
  2026-10-18, вариант B: она публикует хэш ID канала — пароля обмена ключами). Звонок без ключа пары сначала
  выполняет обмен; не вышло за несколько секунд — пользователь видит, что у собеседника старая версия или он
  не в сети.
- **FR-010**: У каждого контакта MUST показываться код проверки (одинаковый у обоих), и пользователь MUST
  мочь отметить контакт «проверен».
- **FR-008**: Обмен ключами MUST NOT требовать от пользователя никаких действий.
- **FR-009**: Ключи MUST храниться так, чтобы приватный ключ не попадал в настройки Vencord, которые
  синхронизируются или экспортируются.

### Key Entities

- **Своя личность**: пара ключей установки, ID устройства.
- **Контакт**: Discord ID, имя, аватар, ключи устройств (каждый со временем добавления и признаком
  «подтверждён»), источник (через какой ЛС получен).
- **Ключ пары**: общий секрет двух устройств, выведенный из их ключей, — им шифруется сигналинг.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Двое с новой версией и общим ЛС получают контакты друг друга без каких-либо действий за ≤ 10 с.
- **SC-002**: Наблюдатель всех событий на релеях не может получить ключ пары ни перебором, ни иначе (нет
  данных, связанных с ключом, кроме шифротекста).
- **SC-003**: Подменённый ключ ни разу не принимается без явного подтверждения пользователя.
- **SC-004**: Звонки между двумя новыми версиями работают так же, как сейчас (время соединения ±1 с).
- **SC-005**: Контакты и ключи сохраняются после перезапуска Discord в 100 % случаев.

## Assumptions

- ID ЛС-канала знают только двое собеседников и Discord; подменить ключи при первом обмене может только
  Discord, и это ловит код проверки.
- Групповые звонки, P2P-чат и офлайн-окно — следующие шаги дорожной карты, не входят сюда; книга контактов
  проектируется так, чтобы они на неё опирались.
- Только Windows, Discord с Vencord, как сейчас.
