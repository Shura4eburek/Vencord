# Research: ключи и контакты

## R1. Почему нынешняя схема подбирается

- Ключ сигналинга = HKDF(`channelId:uidLo:uidHi`). ID канала — снежинка Discord: ~42 бита времени создания
  в мс + мало энтропии в остальных битах, на практике ~40 бит.
- На релеи уходит `pairHint = sha256("p2pcall-v1:pair:" + channelId)` в теге `c` каждого `ring` — проверка
  догадки офлайн за один хэш. Даже без подсказки шифротекст XChaCha20-Poly1305 на релеях проверяет догадку
  по тегу аутентификации. Итог: офлайн-перебор, доступный любому наблюдателю релеев.

## R2. PAKE: CPace на ristretto255

- **Decision**: CPace по `draft-irtf-cfrg-cpace` (вариант `CPACE-RISTR255-SHA512`), пароль `PRS` =
  `channelId` (+ отсортированные user ID в `CI`). Генератор `g = deriveToCurve(SHA-512(DSI ‖ PRS ‖ zpad ‖ CI ‖ sid))`
  (one-way map RFC 9496, в `@noble/curves` — `ristretto255_hasher.deriveToCurve`), `Y = g·y`, `K = y·Y'`,
  `ISK = SHA-512(DSI_ISK ‖ sid ‖ K ‖ transcript)`.
- **Почему стойко**: сообщения CPace — случайные точки группы, по ним догадку об ID канала проверить нельзя.
  Проверка возможна только живым обменом с плагином собеседника → ограничение частоты (R6).
- **Тесты**: векторы из приложения драфта для ristretto255; плюс свойства: одинаковый PRS → одинаковый ISK,
  разный → разный; точка-ноль и некорректная кодировка отвергаются.
- **Alternatives**: SPAKE2 — нужны фиксированные M/N и аккуратная генерация; OPAQUE — асимметричный, нужен
  сервер; прямой DH без пароля — нет аутентификации.
- **Зависимость**: `@noble/curves@2.0.1` уже в дереве (через `nostr-tools`), делаем прямой зависимостью той
  же версии — в бандл ничего нового не добавляется.

## R3. Постоянные ключи и ключ пары

- **Decision**: у установки пара X25519 (`x25519` из `@noble/curves`) + случайный `deviceId` (16 байт).
- После CPace стороны шлют, зашифровав ключом из ISK: свой публичный ключ, `deviceId`, MAC подтверждения
  (HMAC-SHA-512(ISK, роль ‖ транскрипт)). Не сошёлся MAC — обмен отброшен.
- **Ключ пары** = HKDF-SHA256(X25519(свой приватный, публичный собеседника), salt = отсортированные deviceId,
  info = "p2pcall-v2 pair"). Им (XChaCha20-Poly1305, как сейчас) шифруется сигналинг с этим устройством.
- **Код проверки** = первые 40 бит SHA-256(отсортированные публичные ключи обоих) → 8 цифр «1234 5678»;
  одинаков у обоих, меняется при смене любого ключа.

## R4. Где хранить

- **Decision**: всё в main-процессе, в `userData`:
  - `p2pcall-identity.bin` — приватный ключ, зашифрованный `safeStorage` Electron (DPAPI на Windows → другие
    пользователи Windows не прочитают, FR-009, edge case);
  - `p2pcall-contacts.json` — книга контактов (публичные данные).
- Приватный ключ не покидает main: рендерер получает только ключи пар (симметричные) через IPC.
- Офлайн-окно (шаг 4 дорожной карты) будет работать с тем же хранилищем — main стартует без серверов Discord.

## R5. Протокол обмена (поверх релеев Nostr)

```
A → линия B:  pake1 { sid, Ya, from: uidA, dev: devA }                 — открытым текстом
B → линия A:  pake2 { sid, Yb, from: uidB, dev: devB, box(pubB, macB) }
A → линия B:  pake3 { sid, box(pubA, macA) }
```

- `sid` выбирает A (16 случайных байт); генератор CPace зависит от него, поэтому A не ждёт вклада B.
  Свежесть для B обеспечивает его случайный скаляр. `ADa`/`ADb` = `userId:deviceId` — личности в транскрипте.
- `box` = XChaCha20-Poly1305 ключом HKDF(ISK, "box"); `mac` = HMAC(HKDF(ISK, "mac"), роль ‖ транскрипт ‖ pub).
- Подтверждение двустороннее: A проверяет MAC B в `pake2`, B — MAC A в `pake3`. Неверная догадка
  злоумышленника стоит ему одного живого обмена; расшифровать `box` из `pake2` без верного ID канала нельзя.
- **Взаимность** (найдено при реализации): после `pake3` у B есть ключ A и доказательство, что у A есть ключ B
  → устройство сразу `mutual`. A этого не знает (pake3 мог потеряться), поэтому B шлёт `pairok` на ключе
  пары; первое сообщение на ключе пары от B делает устройство `mutual` у A. Пока ключ у A не взаимный, A
  повторяет обмен (раз в 10 мин при открытии ЛС/звонке) — так B получит ключ, если `pake3` потерялся.
  Прежняя схема при наличии любого ключа не используется (ревью: она публикует хэш ID канала — пароля обмена).
- **Когда запускается** (после ревью): только при открытии ЛС и звонке. Стартовая рассылка по 20 ЛС убрана —
  `pake1` несёт ID отправителя открытым текстом и выдавала бы релеям круг общения.

- B находит `channelId` по ЛС с `from` (Discord-сторы). Нет ЛС с таким пользователем → молча игнор.
- Подделать `from` бесполезно: без ID канала ISK не совпадёт, MAC не сойдётся.

## R6. Ограничение попыток

- Ответ на `pake1`: не больше 5 в минуту от одного `from` и 30 в минуту всего; лишнее молча игнорируется.
- Ответчик, не получивший `pake3` за 30 с, — это неудачная догадка (угадывающий проверяет её по `pake2` у
  себя и `pake3` не шлёт) → пауза 1 мин для этого `from` от истечения сессии.
- Итог: ≤ 30 догадок в минуту (~43 000 в сутки) против ~2⁴⁰ вариантов — порядка 70 000 лет (SC-002).
- Подделки (`pake2`/`pake3` с чужим содержимым, `pake1` с занятым `sid`) не обрывают идущий обмен: сессия
  удаляется только после проверки MAC.
- Прежняя схема отключена совсем (вариант B, решение пользователя после ревью): она публиковала хэш ID
  канала, по которому пароль CPace подбирался офлайн. Цена — со старыми версиями звонков нет, пока они не
  обновятся (у всех автообновление). Звонок без ключа пары запускает обмен (повтор не чаще 15 с) и ждёт до 8 с.

## R7. Сигналинг с контактами

- `ring` к контакту: тег `c` = HMAC-SHA256(ключ пары, "hint" ‖ день UTC)[:16] вместо хэша ID канала —
  не связывается между днями и не даёт ничего для перебора. Получатель сверяет с подсказками своих
  контактов (сегодня и вчера, для полуночи).
- Сообщения звонка шифруются ключом пары; у пользователя с несколькими устройствами — по событию на
  каждое его устройство.
- **Переход (Q3 A)**: нет контакта → прежняя схема. Есть взаимный доверенный ключ → сообщения
  прежней схемы от этого пользователя отбрасываются.

## R8. Смена ключа

- Новое устройство или переустановка = новый `deviceId`/ключ у известного контакта → устройство сохраняется
  как «ожидает подтверждения», звонки с ним не принимаются, уведомление «у X новый ключ — новое
  устройство или подмена; сверь код». Подтверждение — в списке контактов.
