# Research: UDP-туннель с автопробросом порта (UPnP)

Источники: живой тест 05.10.2026 (`p2p-nat-findings.md`, локально), диагностика 17.10.2026 (обе стороны:
обычный NAT, релеи доступны, звонок не соединился), код плагина `src/userplugins/p2pCall/`.

## R1. Как подсунуть WebRTC туннель, не трогая Chromium

- **Decision**: туннель — пара UDP-сокетов в main-процессе. WebRTC в рендерере получает
  дополнительный удалённый ICE-кандидат `typ host` на **собственный LAN-адрес ПК** и порт
  локального прокси-сокета туннеля. Каждая сторона добавляет такой кандидат *сама себе* (не через
  сигналинг). Для WebRTC собеседник «сидит» на `192.168.x.y:Lproxy`; прокси пересылает всё через
  туннельный сокет собеседнику, а тот отдаёт своему WebRTC со своего прокси-сокета.
- **Rationale**: ICE-проверки идут «запрос → ответ с того же адреса» только между WebRTC и прокси на
  одной машине, поэтому несимметричный маршрут провайдера ICE больше не видит. DTLS/SRTP остаются
  сквозными — туннель видит только шифрованные байты (FR-011). Ничего не нужно патчить в Chromium.
- **Почему LAN-адрес, а не 127.0.0.1**: Chromium по умолчанию не собирает loopback-кандидаты, а сокет,
  привязанный к LAN-IP, гарантированно может слать на свой же LAN-IP (на Windows и на Linux).
  LAN-адрес берём как локальный адрес маршрута по умолчанию (UDP `connect` к внешнему адресу →
  `address()`), что заодно отсекает Radmin/Hamachi/Hyper-V адаптеры.
- **Приоритет кандидата**: ниже любого `srflx`, на уровне `relay` — если обычный путь работает, ICE
  выберет его (FR-002, SC-003).
- **Alternatives**:
  - чистый WebRTC + UPnP-проброс порта WebRTC: отвергнут — ответы ICE приходят с внутреннего 100.x
    адреса, а не с того, куда ушёл запрос, проверка пары не проходит (риск из отчёта, §4);
  - TURN (свой/Cloudflare): отвергнут пользователем (платно/настройки);
  - `--force-fieldtrials`/флаги Chromium: нет доступа к командной строке Discord до старта, хрупко.

- **Проверено (T001, 2026-10-17)**: Chrome 155 через `puppeteer-core`, два `RTCPeerConnection` без
  своих кандидатов, каждому — удалённый `typ host` на адрес UDP-прокси на Node. И `192.168.1.102`, и
  `127.0.0.1`: ICE `connected`, data channel доставил сообщение, выбрана пара на адрес прокси; у каждой
  стороны ровно один источник (Radmin/Hamachi в пары не попали). Остаётся подтвердить в Discord
  (Chromium 148) на живом тесте. Решение не меняется: LAN-адрес.

## R2. Несколько локальных сокетов WebRTC на одном прокси

- **Decision**: прокси запоминает все источники (`ip:port`), с которых WebRTC шлёт на него, со временем
  последней активности. Входящие из туннеля пакеты классифицируются по первому байту (RFC 7983):
  STUN (0–3) — рассылаются всем живым источникам; DTLS/RTP/RTCP (20–63, 128–191) — только «медиа-источнику»,
  то есть последнему источнику, отправившему не-STUN пакет (до его появления — всем). Источник
  забывается через 30 с тишины.
- **Rationale**: ICE на стороне WebRTC сформирует пары со всех своих локальных сокетов на один удалённый
  адрес; ответ на проверку, пришедший «не в тот» сокет, просто игнорируется по transaction id. После
  выбора пары медиа идёт с одного сокета — его и узнаём.
- **Alternatives**: id потока в заголовке туннеля + отдельный прокси-сокет на каждый поток —
  сложнее и требует согласования, выгоды нет.

## R3. Формат пакета туннеля и опознание собеседника

- **Decision**: заголовок 14 байт: `magic "P2T1"` (4) · `token` отправителя (8) · `path` (1, на какой
  адрес получателя отправлено: 0 = публичный, 1 = наблюдаемый) · `kind` (1: 0 = данные, 1 = keepalive).
  Токен — 8 случайных байт на звонок, передаются только внутри зашифрованного сигналинга. Пакеты с
  чужим токеном или без magic отбрасываются (FR-006).
- **Keepalive**: каждые 1 с до первого пакета от собеседника, затем каждые 2 с (держит маппинги
  NAT/CGNAT). Тело keepalive — битовая маска `path`, по которым сторона *получает* пакеты.
- **Send-to-both (FR-005)**: keepalive всегда идут на оба адреса. Данные — на те `path`, которые
  собеседник подтвердил в своём keepalive; пока подтверждений нет — на оба. Так рабочий маршрут
  находится сам, а аплинк не удваивается после схождения (демка 12–15 Мбит/с).
- **Rationale**: прототип 05.10 доказал «accept by claim, send to both»; маска `path` — дешёвое
  улучшение против удвоения трафика.
- **Alternatives**: HMAC каждого пакета — лишнее: содержимое уже защищено DTLS/SRTP, токен лишь
  отсекает мусор; слать данные всегда на оба адреса — удваивает аплинк.

## R4. UPnP IGD

- **Decision**: собственная минимальная реализация на `dgram` + `http` (без зависимостей):
  1. SSDP `M-SEARCH` (`ST: urn:schemas-upnp-org:device:InternetGatewayDevice:1`), сокет привязан к
     LAN-адресу маршрута по умолчанию (замер 17.10: без привязки ответ не приходит при нескольких
     адаптерах), ожидание 1,5 с;
  2. `GET LOCATION` → XML → `controlURL` сервиса `WANIPConnection:1|2` или `WANPPPConnection:1`;
  3. SOAP `AddPortMapping` (UDP, внешний = внутренний = P, `NewInternalClient` = LAN-IP,
     описание `P2PCall`, `LeaseDuration` 600 с); при ошибке 725 (OnlyPermanentLeasesSupported) — повтор с 0;
     при 718 (ConflictInMappingEntry) — следующий порт;
  4. продление каждые 5 мин, пока звонок идёт; `DeletePortMapping` при завершении звонка, выключении
     плагина и `before-quit` (FR-003, FR-004, SC-004).
- **Порт**: случайный из 40000–40999, до 5 попыток при конфликте.
- **Rationale**: ASUS (роутер друга) по умолчанию держит miniupnpd; зависимость ради ~150 строк не нужна.
- **Alternatives**: NAT-PMP/PCP — у ASUS тоже есть, но вне рамок v1; пакет `nat-upnp` — лишняя
  зависимость в main-процессе Discord.

## R5. Публичный адрес туннеля

- **Decision**: STUN Binding с самого туннельного сокета к `stun.l.google.com:19302` и
  `stun.cloudflare.com:3478` (те же, что у WebRTC). Берётся первый ответ, таймаут 2 с. Если
  адреса разные (симметричный NAT) — всё равно публикуем первый, в лог пишем предупреждение.
- **Rationale**: проброс UPnP открывает порт на роутере, но CGNAT может сменить внешний порт; правду
  знает только STUN (замер 05.10: у Mamoru порт не сохраняется).

## R6. Когда поднимать туннель (тайминг)

- **Decision**: подготовка (сокеты, UPnP, STUN) у звонящего стартует при `outgoing` (пока идёт вызов),
  у принимающего — при «Принять» (`connecting`): входящий звонок сам по себе не открывает порт на роутере
  (замечание ревью). Адреса отправляются собеседнику сообщением `tun` при
  `start-session` (и повторно, если подготовка закончилась позже). `iceTimeoutSec` по умолчанию 10 с —
  туннель обязан уложиться: SSDP 1,5 с + SOAP < 0,5 с + STUN < 0,5 с.
- Добавленный после `failed` кандидат Chromium проверяет заново (состояние уходит в `checking`).
- После `restartIce()` (новые ufrag) кандидат туннеля добавляется заново после следующего
  `setRemoteDescription`.

## R7. Где жить коду и IPC

- **Decision**: `tunnel.ts` — чистая логика без Electron (сокеты через инъекцию `dgram`), `upnp.ts` —
  SSDP/SOAP, оба импортируются из `native.ts` (main). Рендерер управляет через
  `VencordNative.pluginHelpers.P2PCall` (как `media.ts`, `updater.tsx`). Пакеты не ходят через IPC.
- **Нагрузка**: демка 15 Мбит/с ≈ 1500 пакетов/с в каждую сторону — для `dgram` в main-процессе
  незаметно.

## R8. Совместимость (FR-013)

- **Decision**: новый тип сигнала `tun` в `SignalType`. Старые версии игнорируют неизвестный тип
  (`controller.onSignal` — `switch` без `default`). Туннель используется, только если `tun` пришёл от
  собеседника.

## R9. Диагностика и подсказка (FR-010, FR-012)

- В лог: `[P2PCall] tunnel` — порт, UPnP (ok / нет IGD / ошибка с кодом), публичный адрес, адреса
  собеседника, подтверждённые `path`, итоговый путь звонка.
- `PathType` получает значение `tunnel`: выбранная пара, у которой удалённый кандидат = адрес прокси.
  Чип: «напрямую (туннель)».
- При `ice-failed`/`ice-timeout`: если у этой стороны UPnP не удался — текст «Включите UPnP на
  роутере»; если у собеседника (из его `tun`) — «У собеседника выключен UPnP на роутере».
